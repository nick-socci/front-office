# Docs site, SQL lint, exposures and the record — requirements

Issue: #13 · Tier: M · Status: draft

## Problem

Sub-project 2 is built: #11 and #12 are closed, and #13 is the last open issue of its
milestone (20 closed, 1 open). What a reader of the repository sees has not kept up, and
nothing checks the SQL's form. Read on 2026-10-09:

- **The lineage is invisible.** 56 models from one raw table to nine marts, and the only
  way to see how they connect is to clone the repo and run dbt. GitHub Pages is not
  enabled on the repository.
- **The README describes a project two milestones old.** It says "Marts and full-season
  matchup reconciliation are still pending", lists staging models only, counts "100
  pytest tests" and "159 nodes" (today: 822 tests; 644 nodes on the fixtures), and its
  roadmap opens with "Marts". `docs/README.md` says sub-project 2 "is underway".
- **Nothing lints SQL.** `ruff` and `mypy` hold the Python to a standard; the 117 SQL
  files under `dbt/models` and `dbt/tests` have only reviewers. sqlfluff with its default
  rules reports 1,843 violations in 105 of them, and cannot parse part of one model.
- **Nothing downstream of the marts is declared.** dbt does not know that an example
  query exists or that a dashboard is planned, so neither appears in the lineage, and
  the one example query (`docs/examples/roster_day_query.sql`) is run by nothing: a
  renamed column would break it silently.

One item of the issue is already done: `raw.api_responses` has had freshness thresholds
(warn 36 hours, error 7 days) since sub-project 1. What is missing there is only the
proof that they work and the statement of why nothing runs them.

## Goals

- A public page where a reviewer sees the DAG from raw JSON to marts, and reads any
  model's description, columns, SQL and tests, without cloning anything.
- SQL held to one written style by a gate, with the one-off reformatting proved to have
  changed no number.
- The marts' consumers declared in dbt, and every declared example kept runnable.
- A README that states what exists, with numbers traceable to a recorded run.

## No-gos

- **No change to any relation.** No model's rows, column names, column order or types
  change (R2.4). A lint rule that can only be satisfied by changing one is turned off,
  not obeyed.
- **Nothing from the real season is published.** The site is built in CI from the
  committed fixtures, never from `data/` and never on a person's machine (R1.1, R1.3).
- **No dashboard.** The exposure declares a plan; `dashboard/` stays empty.
- **No scheduled freshness run, and no change to the thresholds.** Freshness stays
  dormant until the 2027 daily schedule (sub-project 3).
- **No per-source freshness.** The raw table holds three sources with different
  cadences; splitting its freshness is a follow-up issue (design, *Open questions*).
- **No linting of macros, of `docs/examples/`, or of Python.** (ADR 0042; ruff already
  covers Python.)
- **No pre-commit lint hook.** The hook stays what it is: the privacy guard.
- **No edit to `docs/design/`.** It is the pre-spec record.
- **An agent does not enable Pages or change repository settings.** That is the
  owner's action (tasks, step 2).

## Rabbit holes

- Chasing zero violations by rewriting SQL to please a rule → every rule left after
  the automatic fix is either fixed by hand in under ten places or turned off with its
  reason written beside it (R2.2). The triage is one task with a stop condition.
- Tuning the docs site's look → dbt's stock site, plus one overview page. No theme, no
  custom JavaScript.
- Guessing which marts each dashboard page will read → the dashboard exposure names
  every mart, and says it is a plan (ADR 0043).
- Rewriting the README from scratch → the listed stale statements are replaced and the
  listed sections added (R5); the rest stands.

## Requirements

### R1. The docs site

A reviewer opens one URL and sees the lineage.

- R1.1 WHEN a commit is pushed to `main` and every earlier CI step has passed, THE
  SYSTEM SHALL deploy to GitHub Pages a site generated by `dbt docs generate --target ci
  --vars '{anonymize: true}'` from the fixture warehouse built in that same run.
- R1.2 WHEN CI runs for a pull request, THE SYSTEM SHALL generate and check the site,
  and SHALL NOT deploy it.
- R1.3 IF the assembled site holds a file other than `index.html`, `manifest.json` and
  `catalog.json`; or a catalog entry whose database is not `ci`; or one of
  `privacy.FORBIDDEN_KEYS` as a JSON key; or a match of `privacy.GUID` anywhere other
  than the values of `metadata.invocation_id` and `metadata.user_id`; THEN THE SYSTEM
  SHALL fail before anything is uploaded, naming what it found.
- R1.4 THE SYSTEM SHALL copy the three files into the site by name, and SHALL NOT
  publish `dbt/target/` or any other part of it.
- R1.5 THE SYSTEM SHALL replace dbt's stock landing page with an overview that says
  what the project is, names the four layers and what each is for, says how to open the
  lineage graph, says the site is built from fixtures and holds no league data, and
  links the repository.
- R1.6 THE SYSTEM SHALL grant `pages: write` and `id-token: write` to the deploy job
  only; every other job keeps the default read-only token.
- R1.7 `.agentic/gates` SHALL run the same generate and check steps, in CI's order.
- R1.8 THE SYSTEM SHALL link the site from the top of `README.md`.

### R2. SQL lint

- R2.1 THE SYSTEM SHALL lint every `.sql` file under `dbt/models` and `dbt/tests` with
  sqlfluff (DuckDB dialect, dbt templater, ADR 0042) in the gates and in CI, and fail on
  any violation, a file it cannot parse included.
- R2.2 THE SYSTEM SHALL keep the rule configuration in one `.sqlfluff` file at the
  repository root, in which every rule turned off or reconfigured carries a comment
  saying why (ADR 0041).
- R2.3 THE SYSTEM SHALL make the one-off reformatting in a commit that holds nothing
  but the output of `sqlfluff fix` on `.sql` files. Hand edits come in a commit before
  it; configuration, dependencies and CI in commits of their own.
- R2.4 IF, on the real 2026 season, the warehouse built after the hand edits and the
  reformatting differs from the one built before them in any relation's rows, column
  names, column order or column types, THEN the build SHALL stop and the difference
  goes to the owner.
- R2.5 THE SYSTEM SHALL build with the same result counts before and after: on the
  fixtures PASS=641 WARN=3 ERROR=0 of 644, and on the real season the counts recorded in task 1.
- R2.6 IF a `-- noqa` comment is added THEN it SHALL name the rule and the reason on
  the same line. The number added is reported on the issue; the target is none.
- R2.7 THE SYSTEM SHALL add `sqlfluff` and `sqlfluff-templater-dbt` to the `dev`
  dependency group at one matching version, in `uv.lock`.
- R2.8 `AGENTS.md` SHALL list the lint command under *Commands*.
- R2.9 THE SYSTEM SHALL list the reformatting commit in `.git-blame-ignore-revs`, so that
  `git blame` and GitHub's blame view skip it.

### R3. Exposures

An exposure is dbt's way to declare something outside dbt that reads its models: a
dashboard, a notebook, a query. It builds nothing; it adds a node at the end of the
lineage and makes `--select +exposure:<name>` mean "everything this needs".

- R3.1 THE SYSTEM SHALL declare one exposure, `front_office_dashboard`, of type
  `dashboard` and maturity `low`, depending on every model in `dbt/models/marts`, whose
  description says it is planned and not built.
- R3.2 THE SYSTEM SHALL declare one exposure of type `analysis` for each `.sql` file in
  `docs/examples/`, depending on exactly the models that file reads.
- R3.3 IF an example file reads a relation its exposure does not name, or its exposure
  names one it does not read, or an example file has no exposure, or an exposure names
  a file that does not exist, THEN the gates SHALL fail and say which.
- R3.4 WHEN the gates run, THE SYSTEM SHALL execute every example file against the
  fixture warehouse and fail on any error.
- R3.5 IF a model exists in `dbt/models/marts` that `front_office_dashboard` does not
  name THEN the gates SHALL fail.
- R3.6 Every exposure's `owner` SHALL carry a name and no email address.
- R3.7 WHEN `dbt build --target ci --select +exposure:<name>` is run for any declared
  exposure, THE SYSTEM SHALL build and test that exposure's upstream models and pass.
- R3.8 *(Only if the owner chooses it — PR, Decisions for you.)* THE SYSTEM SHALL add
  three example files, one per question the marts answer (matchup results, player
  value, lineup decisions), each reading marts only, naming no fantasy team, and each
  with its exposure.

### R4. Source freshness

Source freshness is dbt's check of how old the newest row of a source table is:
`dbt source freshness` compares `max(loaded_at_field)` with now and warns or errors past
the thresholds in the source's YAML.

- R4.1 `raw.api_responses` SHALL keep `warn_after` 36 hours and `error_after` 7 days on
  `fetched_at` read as UTC. This spec does not change them.
- R4.2 WHEN `dbt source freshness` is run on the real warehouse, THE SYSTEM SHALL report
  an age equal to the time since the newest capture, to the minute.
- R4.3 No gate and no CI job SHALL run `dbt source freshness`. (The fixtures' newest
  capture is 2026-05-02; it errors there by design.)
- R4.4 The source YAML and the README SHALL say that freshness is dormant, why (no
  schedule exists, fixtures are stale by design), what wakes it (the 2027 daily
  schedule), and its known limit (one age for a table holding three sources).

### R5. README and the record

- R5.1 `README.md` SHALL hold, under the heading `## The marts`, a table with one row
  per mart: name, the question it answers, its grain, and its row count on the 2026
  season.
- R5.2 IF a model in `dbt/models/marts` has no row in that table, or a row names
  something that is not a mart, or a row has an empty cell, THEN a test SHALL fail.
- R5.3 `README.md` SHALL state the reconciliation against ESPN with its numbers: how
  many category results and matchup stat values were compared, how many matched, and
  what each kind of non-match is.
- R5.4 `README.md`'s layer table SHALL cover staging, intermediate, marts and
  reconciliation; its roadmap SHALL start at what is not built, name built marts by
  their `fct_`/`dim_` names, and link the docs site.
- R5.5 Every count in `README.md` (tests, nodes, rows) SHALL come from a run whose
  command and output are recorded on #13, dated.
- R5.6 `README.md` SHALL no longer say that marts or reconciliation are pending, that
  the project has 100 pytest tests or 159 nodes, or "Thirty tests enforce it" (today 11
  functions in `test_fixture_privacy.py`; the build states the real number or none).
- R5.7 `docs/README.md` SHALL mark sub-project 2 complete and list the specs and ADR
  directories under *What is here*.
- R5.8 Nothing this work adds to a README, an example or the overview SHALL name a
  fantasy team or a league member.
