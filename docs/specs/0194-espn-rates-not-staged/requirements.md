# ESPN's rate stats are not staged — requirements

Issue: #194 · Tier: M (confirmed by the owner, 2026-10-24) · Status: draft

## Problem

ESPN's game lines carry rates as well as counts (AVG, ERA, WHIP, K/BB and others), and a
rate whose denominator is zero has no value. ESPN writes one anyway, in an encoding that
changes with the season and the endpoint (design.md, C2 to C6):

- in the 2018 game lines, the largest double, 1.7976931348623157e308: 1,781 values;
- in the 2019 to 2026 game lines, `0.0`: about 2,000 K/BB lines a season and about 35
  ERA lines, each of which reads as a perfect rate;
- in the 2021 game lines, NaN for runs created (stat 19): 4,076 values;
- in the matchup lines, the string `"Infinity"`, which spec 0147 (R1.5) already drops.

Two of the 2018 values in one sum overflow it. DuckDB gives infinity; BigQuery stops
with "floating point overflow". That is how #135 found them (PR #192, task 13). Nothing
reads ESPN's rates today: the readers of both line models take count stats only (C8), and
rule 4 keeps the project's own numbers off rates. But a future reader would take ESPN's
undefined rates for numbers.

## Goals

- No ESPN rate is staged, so no model can read an undefined rate as a number, in any of
  its encodings, or sum two sentinels into an overflow.
- What counts as a rate is written down once, generated into a seed, and read by both
  ESPN line models.
- A test fails if a listed rate reaches either model, or if a value is non-finite or at
  least 1e300. The second catches an x/0 sentinel or a NaN in any stat, listed or not. It
  cannot catch an unlisted rate that ESPN writes as `0.0`: that rate passes as a count
  until it is named (design.md, *Risks*).
- Every row of every stat id that is kept is unchanged, and so is every reconciliation
  result (C9). "Rate" here includes RC, which is derived from other stats rather than a
  ratio: like the rates, it is no count, and its undefined value is ESPN's NaN (C5).

## No-gos

Work that drifts into any of these is escalated, not done.

- No model computes or stores a rate. The project's own rates come from components (rule
  4), and that does not change.
- No reinterpretation of a count. A count stat that ESPN writes oddly is out of scope;
  the value test would surface it, and it would get its own issue.
- No rate is nulled in place, and no flag column is added. The owner chose not to stage
  rates at all (ADR 0099).
- No change to which stats a reconciliation compares, or how.
- No edit by hand to `espn_stat_ids.csv`. The column is generated by
  `scripts/make_espn_seeds.py`, as the rest of the seed is.
- No new classification of the 7 stat ids that espn-api does not name (22, 30, 61, 64,
  78, 79, 80). They stay out of the seed and are kept by both models, as they are now.

## Rabbit holes

- **Telling a rate from a count by its values.** WPCT and SV% hold only 0 or 1 in a game
  line, and the 7 unnamed ids hold only whole numbers (C7). → An explicit list of
  the rates, a constant in `make_espn_seeds.py` (ADR 0099).
- **Each rate's formula, to null it only at a zero denominator.** Only 4 of the 15 rates
  are in `espn_stat_components.csv` (C7). → Not staged at all, so no formula is needed.
- **The meaning of RC's NaN.** RC has other terms besides AB + BB, and other seasons give
  it a real value on such lines (C5). → It is a rate in the list, so it is not staged,
  and what ESPN meant by the NaN does not matter here.
- **The matchup lines' `"Infinity"`.** R1.5 of spec 0147 already drops it (C6). → That
  rule stays. The new rule drops the defined rates beside it, so that the two models mean
  the same thing by "ESPN's lines".

## Requirements

### R1. The list of rates

- R1.1 THE SYSTEM SHALL generate a boolean column `is_rate` in `espn_stat_ids.csv` from a
  constant in `scripts/make_espn_seeds.py`, true for exactly these 15 stat ids, the rates
  and the one derived value (RC) in ESPN's lines: 2 (AVG),
  9 (SLG), 17 (OBP), 18 (OPS), 19 (RC), 29 (PPA), 38 (OBA), 41 (WHIP), 43 (OOBP),
  47 (ERA), 49 (K/9), 55 (WPCT), 59 (SV%), 71 (FPCT), 82 (K/BB), and false for every
  other stat id in the seed.
- R1.2 IF the constant names a stat id that is not in espn-api's `STATS_MAP`, THEN THE
  SYSTEM SHALL stop the seed generation, naming the id.
- R1.3 THE SYSTEM SHALL fail a data test if `espn_stat_ids.is_rate` is null.

### R2. The line models stage counts only

- R2.1 THE SYSTEM SHALL leave out of `stg_espn__player_game_stats` every row whose
  `stat_id` has `is_rate` true.
- R2.2 THE SYSTEM SHALL leave out of `stg_espn__matchup_player_lines` every row whose
  `stat_id` has `is_rate` true.
- R2.3 WHEN a stat id is not in `espn_stat_ids`, THE SYSTEM SHALL keep its rows in both
  models, as it does now.
- R2.4 THE SYSTEM SHALL leave every other row of both models unchanged: same keys, same
  value.

### R3. Tests

- R3.1 IF either line model holds a row whose `stat_id` has `is_rate` true, THEN THE SYSTEM
  SHALL fail a data test that names the model and the stat id.
- R3.2 IF either line model holds a `stat_value` that is NaN, infinite, or has an absolute
  value of at least 1e300, THEN THE SYSTEM SHALL fail a data test that names the model,
  the stat id and the value.
- R3.3 THE SYSTEM SHALL commit a plant in `dbt/plants/` for each of R3.1 and R3.2, showing
  each test fail on a planted row in each model. The CI fixtures cannot hold such a row
  (C10).
- R3.4 THE SYSTEM SHALL write the R3.2 test once for both warehouses, through a dispatched
  `fo_is_finite` macro: DuckDB's `isfinite`, and on BigQuery `not is_nan(x) and not
  is_inf(x)`.

### R4. Downstream

- R4.1 WHEN the real season is built, THE SYSTEM SHALL leave every reconciliation model
  downstream of the two line models row-for-row identical (C9).
- R4.2 THE SYSTEM SHALL say in each line model's opening comment, and in its YAML
  description, that ESPN's rates are not staged, and why (ADR 0099).
