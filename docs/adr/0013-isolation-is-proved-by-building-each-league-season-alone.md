# 0013. Isolation is proved by building each league-season alone

- Status: proposed
- Date: 2026-10-04
- Spec: [0028-league-season-identity](../specs/0028-league-season-identity/design.md) · Issue: #28

## Context

#28 is done when two leagues by two seasons build "without loss, duplicates or
cross-attribution". Loss and duplicates are visible to ordinary tests. Cross-attribution
is not: a pool sized by every league's teams, or a window bounded by another season's
dates, produces plausible rows that pass uniqueness and not-null. The warehouse has 39
relations and more will come; reading each one for a missing join key does not scale and
does not stay true.

## Decision drivers

- The check must name the model that leaks, not just fail.
- It must cover models written later, without anyone remembering to extend it.
- No league members' data, and no second real league.
- CI time.

## Considered options

1. **Equivalence with single builds** — build the combined fixture, build each
   league-season on its own, and require every model's rows for that league-season to be
   identical in both.
2. **Per-model tests** — uniqueness on full keys and relationship tests with league and
   season, written model by model.
3. **Make the main CI fixture two leagues by two seasons** — every existing test then
   runs under multiplicity.

## Decision

Chosen: **equivalence with single builds**, as a gate. A second committed fixture holds
four league-seasons, generated by script from the existing fixture: a relabelled second
league sharing every fetch timestamp, and a 2027 season of one scoring period with MLB
games moved to its date. A script builds it, builds each league-season alone with only
its own season's MLB data, and compares every relation as a multiset: by league-season
where the relation has those columns; where it does not, the single build's rows must
all be in the combined one. A relation that depends on a league but lacks the columns
therefore differs, and so does one that reads another season's MLB rows; both are named.

Per-model tests are still written (R3.3), but they prove keys, not arithmetic. Making the
main fixture multi-tenant would change every fixture row count and still not show that a
pool or a window used the right league.

## Consequences

- Good: one check covers every present and future model.
- Bad / accepted cost: four extra model builds per gate run (the combined one with tests,
  three single ones without; the fourth single build is the existing CI build). Measured
  when built; expected well under a minute on fixtures.
- Bad / accepted cost: the extra league-seasons are copies, so the check proves isolation
  and nothing about whether a real second league's data is handled.
- Bad / accepted cost: a second fixture root to keep generated, never hand-edited.
- Follow-ups: none.
