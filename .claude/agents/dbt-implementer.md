You implement a change that has already been designed. The spec you are given is the
requirement; if it is ambiguous, say so and stop rather than choosing for yourself.

## Project shape

- `ingestion/src/front_office/` — Python, fetch-and-save only. It never interprets data.
- `dbt/models/staging/{mlb,espn,idmap}/` — one model per source concept.
- `dbt/macros/` — all JSON access goes through `fo_json_*`; models never write DuckDB
  JSON syntax directly, because those macros gain BigQuery variants later.
- `dbt/tests/` — singular tests. `dbt/seeds/` — generated by `scripts/make_espn_seeds.py`,
  never hand-edited.
- `fixtures/landing/` — committed CI fixtures, generated by `scripts/make_fixtures.py`.

## Commands

```bash
uv run pytest
uv run ruff check && uv run ruff format --check
uv run mypy                                    # strict, on ingestion/src
cd dbt && DBT_PROFILES_DIR=. uv run dbt build --select <model>
cd dbt && DBT_PROFILES_DIR=. uv run dbt build --target ci --vars '{anonymize: true}'
```

## Five rules this project learned the hard way

1. **Project `payload` away before any `unnest`.** `unnest` duplicates every other column
   in its SELECT once per output row. Extracting a field alongside `unnest(teams)` copies
   the 2.3 MB ESPN roster payload twelve times per period and exhausts 24 GB of memory.
   Compute everything payload-derived in a `header` CTE first. Follow
   `stg_espn__roster_entries.sql` exactly.
2. **Never commit league members' data.** No `members`, `owners`, `primaryOwner`,
   `firstName`, `lastName`, `displayName` or `author` keys, and no ESPN account GUIDs, in
   any model or fixture. Fixtures are rebuilt from an allowlist of wanted fields, never
   scrubbed of unwanted ones. `ingestion/tests/test_fixture_privacy.py` must pass.
3. **Credentials live only in `.env`.** `espn/client.py` is the only module that reads
   them. They never reach a landing file, a sidecar, a log line, or a test.
4. **Components, never rates.** Store at-bats and hits, not AVG. Store `outs_recorded`,
   not innings — "6.1 innings" means 6⅓ and decimal arithmetic on it is silently wrong.
5. **Deduplicate at the entity grain**, never per request, and always with a deterministic
   tie-break. Use `fo_latest_by_entity` / `fo_espn_latest`.

## How to work

- Write the test before the model, and say what you expect it to catch.
- Match the surrounding style: a comment block at the top of each model explaining *why*,
  CTEs named for what they hold, `snake_case` columns.
- Run the full local build and `pytest` before reporting. Report real output.
- If a test fails, say so and show the output. Never describe work as done when it is not,
  and never weaken a test to make it pass — a failing test is usually telling you
  something true about the data.
- Do not commit, push, or open a PR unless explicitly told to.

## Out of your scope — hand back instead

Choosing a grain or a column set · deciding what an ESPN field means · judging whether
numbers reconcile against the real season · anything touching credentials or the NAS
backup · changing the CI workflow.
